# Godot 4: a extensão só carrega no build de motor com a mesma precisão de float

## Em uma frase
Extensões são compatíveis apenas com builds do motor que usam o mesmo nível de precisão de ponto flutuante da compilação — e os builds double exigem o extension_api.json gerado pelo seu próprio motor custom.

## Por que importa
Coordenadas de mundo em single são um default de motor que vira ABI: trocar single por double muda o layout das estruturas trocadas com o motor. A doc é explícita no mecanismo ('the extension must also be compiled for double-precision floats and use an extension_api.json file generated by your custom engine build') porque grandes mundos (large world coordinates) dependem do double — e é a fronteira onde 'funcionava no desktop' morre em port.

## Como funciona
Para o caso duplo (literal): o build do motor com single é o default; extensões single/single rodam nele. Um motor customizado com 'precision=double' exige extensão compilada em double E o JSON de API gerado por aquele build (não o do release oficial) — a própria página aponta o processo na seção de build system (scons). A regra geral: 'if you build a custom version of Godot, you should generate an extension_api.json from it', porque seu motor pode divergir do oficial no que expõe. Declare a matriz (plataforma × precisão × versão) nos seus artefatos.

## Exemplo
Um jogo de espaço 4X usa double para posições orbitais; o plugin de física compila dois sets de binários (single e double) referenciados pelas linhas 'double'/'single' na seção [libraries] — a flag de arquitetura da doc é exatamente para isso.

## Limites e trade-offs
A flag double/single é uma escolha de compilação do motor, não um toggle de runtime para o jogador. extension_api.json de build custom desatualizado é um erro silencioso até a primeira divergência — trate o arquivo como artefato versionado junto do motor. Port web tem sua via (wasm32), e o resto da matriz continua valendo.

## Como verificar
Rode a extensão single no motor double e confirme a recusa/falha documentada — é a regra como teste. Gere o extension_api.json do seu build custom, diff contra o oficial e registre o que divergiu; o diff é a evidência de por que a regra existe. Na lib do produto, as duas flags de arquitetura aparecem com caminhos distintos.
