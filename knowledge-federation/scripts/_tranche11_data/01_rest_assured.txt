restassured-given-when-then-fronteira||REST Assured: separar preparação, chamada e assertions||O padrão given/when/then organiza a especificação da requisição, a execução do HTTP e as expectativas sobre a resposta.||Assertions distribuídas em helpers pouco claros podem ocultar qual entrada produziu um status ou corpo inesperado.||Monte headers, parâmetros e corpo no given, faça a chamada identificável no when e valide status, headers e campos de resposta no then.||Um teste POST configura JSON e token, envia a criação de pedido e verifica status 201, tipo de conteúdo e identificador devolvido.||A DSL melhora leitura, mas não define por si só se a chamada é unitária, de integração ou contra um serviço externo.||Compare o request construído com o contrato e verifique que cada assertion aponta para uma saída observável relevante.||ra_usage,ra_response||A documentação descreve a DSL como configuração da request, execução e validação da resposta, sem atribuir à sintaxe uma fronteira de teste automática.
restassured-request-specification-reuso-isolado||REST Assured: reutilizar request specification sem compartilhar mutações||RequestSpecification agrupa dados de request que podem ser compostos e reaproveitados em várias chamadas.||Duplicar base URI, headers comuns e autenticação em cada caso cria divergência; um objeto global mutável pode, por outro lado, vazar dados entre testes.||Construa uma specification comum para invariantes e derive ou crie uma configuração por cenário quando parâmetros e headers mudarem.||Uma specification base define host e Accept; cada teste cria sua própria cópia lógica com token e path parameter do usuário em teste.||O merge de specifications tem regras próprias para campos sobrescritos e mesclados; não presuma que toda propriedade é acumulada.||Execute os casos em paralelo e em ordem aleatória e confirme que host, autenticação e parâmetros permanecem associados ao cenário certo.||ra_request,ra_core||A API expõe specifications reutilizáveis; o uso de escopo por cenário evita depender de estado estático compartilhado.
restassured-response-specification-contrato-comum||REST Assured: compartilhar expectativas de resposta sem mascarar exceções||Uma response specification permite reutilizar assertions comuns para respostas de vários testes.||Se cada cenário validar somente status, mudanças de Content-Type ou headers obrigatórios podem passar despercebidas; uma especificação genérica demais também pode impor expectativas sem relação com o caso.||Defina um conjunto enxuto de invariantes comuns, como tipo de conteúdo ou header de segurança, e mantenha no teste as assertions específicas do endpoint.||Vários GET validam application/json por specification comum, enquanto cada teste verifica seus próprios campos e semântica de status.||A API e a forma de declarar a specification variam conforme a versão usada; não compartilhe uma specification que o teste modifica.||Faça um teste de controle que remova cada header obrigatório e confirme que a expectativa compartilhada falha pelo motivo esperado.||ra_response,ra_usage||As páginas mostram expectations de resposta e builders reutilizáveis; a decisão de escopo foi limitada a invariantes comuns.
restassured-path-query-parameters-distintos||REST Assured: distinguir path parameters de query parameters||Path parameters substituem segmentos nomeados do caminho; query parameters são enviados na parte de consulta da URL.||Usar ambos como um único texto de URL dificulta variar identificadores e filtros e pode produzir encoding ou ordenação frágil.||Declare o identificador de recurso como path parameter e filtros ou paginação como query parameters, sem concatenar valores manualmente.||O teste faz GET em /orders/{orderId} com orderId dinâmico e envia status=pending como parâmetro de consulta independente.||Convenções de encoding e valores repetidos dependem da configuração e do contrato HTTP esperado pelo servidor.||Inspecione a URL efetivamente recebida pelo servidor de teste para validar caminho, nomes, multiplicidade e encoding de parâmetros.||ra_usage,ra_request||A Usage Wiki documenta path parameters nomeados e parâmetros de request separadamente; a recommendation mantém semânticas distintas.
restassured-object-mapping-dependencias-explícitas||REST Assured: verificar dependências exigidas por object mapping||REST Assured pode serializar objetos Java para JSON ou XML e desserializar respostas quando os mapeadores compatíveis estão disponíveis no classpath.||Um teste que passa na máquina de desenvolvimento pode falhar no CI se o runtime não incluir o mapper ou se o Content-Type não selecionar o formato pretendido.||Declare o módulo de mapper exigido pelo projeto, envie DTO representativo e indique o tipo de conteúdo esperado na request.||O teste envia um DTO de criação como JSON e confirma que o servidor recebeu nomes e tipos coerentes com o modelo wire.||O formato concreto depende dos mapeadores instalados e da configuração; DTO Java não comprova sozinho compatibilidade com schema externo.||Execute com as mesmas dependências do CI e verifique o corpo serializado e o Content-Type no servidor de teste.||ra_mapping,ra_request||A documentação condiciona o mapeamento à presença de providers compatíveis no classpath e ao formato de conteúdo da chamada.
restassured-jsonpath-extrair-depois-de-validar||REST Assured: extrair valores JSON após validar a resposta||JsonPath permite selecionar valores do corpo JSON da resposta para assertions ou etapas posteriores do teste.||Extrair um campo sem primeiro validar status e formato pode transformar uma resposta de erro em falha secundária confusa.||Valide primeiro status e Content-Type; então extraia o campo relevante e compare seu valor ou use-o em uma chamada subsequente controlada.||Um GET de pedido verifica status 200 e JSON antes de extrair o id para consultar uma rota de detalhe.||JsonPath verifica caminhos e valores escolhidos, mas não prova que todos os campos ou a estrutura completa obedecem a um schema.||Substitua o status de sucesso por erro e confirme que o teste falha na assertion de protocolo antes da extração do campo.||ra_usage,ra_response||A Usage Wiki documenta extração e validação de dados de resposta; a nota separa validação de HTTP de projeção JSON.
restassured-json-schema-validacao-opcional||REST Assured: tratar JSON Schema como validação configurada||REST Assured oferece matcher para validar um corpo JSON contra um schema, disponível pela integração de validação correspondente.||Verificar poucos campos pode deixar propriedades obrigatórias, tipos ou estruturas aninhadas incompatíveis com o contrato passar despercebidas.||Inclua a dependência de JSON Schema Validator, carregue schema versionado e aplique o matcher à resposta que já teve status validado.||A resposta de listagem é conferida contra schema que exige id e name em cada item e define o tipo de price.||O schema precisa refletir a versão de contrato pretendida; matcher não verifica regras de negócio nem que o schema esteja correto.||Altere um tipo obrigatório de resposta em um teste negativo e confirme que o matcher reporta o caminho do campo inválido.||ra_schema,ra_usage||A documentação oficial mostra o matcher matchesJsonSchemaInClasspath; sua disponibilidade depende do módulo e do schema usado.
restassured-filtros-logging-nao-e-wire-capture||REST Assured: não confundir logging de filtro com captura exata no wire||Filters podem observar ou alterar request antes do envio e response antes das expectations; filtros também podem implementar logging ou autenticação.||O log de uma especificação não é necessariamente a requisição final: cliente HTTP pode adicionar headers e filtros posteriores ainda podem modificá-la.||Use filtros para comportamento transversal e diagnóstico; para prova do que chegou, observe o request em servidor controlado ou proxy de teste.||Um teste confirma no servidor um header inserido por filtro posterior, em vez de inferir sua presença apenas pelo log pré-envio.||Logs podem conter tokens, cookies e corpos pessoais; redija segredos e não os publique como artefato irrestrito.||Compare log, ordem de filtros e request observado no stub e confira política de redaction antes de habilitar logging em CI.||ra_filters,ra_usage||A documentação explica o ciclo do filter e limita logging à specification observada, não a uma captura garantida do tráfego final.
restassured-auth-por-caso-sem-credencial-em-log||REST Assured: configurar autenticação por teste e proteger credenciais||REST Assured suporta esquemas de autenticação e configuração de credenciais por request.||Credenciais estáticas globais podem ser herdadas por testes indevidos e aparecer em logs, fixtures ou mensagens de falha.||Leia credenciais de mecanismo de teste isolado, associe autenticação à chamada que precisa dela e aplique filtros de logging com redaction.||Um caso usa token sintético de curta duração para GET protegido; outro confirma 401 sem token sem reutilizar credencial de produção.||O suporte do cliente não valida a política de autorização do servidor; respostas precisam ser verificadas em ambiente controlado.||Procure tokens nos relatórios gerados e confirme que o teste negativo permanece independente da execução do caso autenticado.||ra_auth,ra_request||A Usage Wiki documenta autenticação e filtros; as recomendações de isolamento e redaction evitam expor dados de teste.
restassured-configuracao-global-reset-e-paralelismo||REST Assured: evitar vazamento de configuração estática entre testes||REST Assured expõe defaults estáticos como base URI, filtros e specifications que influenciam requests posteriores.||Uma alteração de host ou parser em um teste pode contaminar outros casos, sobretudo quando a suíte roda em paralelo.||Prefira configuração local por request e restaure explicitamente qualquer default global alterado pelo teste.||Um teste aponta baseUri para um mock local e limpa a configuração no teardown; outro confirma que continua usando seu próprio destino.||Reset global durante execução paralela também pode afetar testes em andamento; limpeza não substitui isolamento concorrente.||Rode a classe em ordem aleatória e com paralelismo habilitado e procure requests enviados ao host de outro cenário.||ra_core,ra_request||A Javadoc lista defaults estáticos; a verificação recomendada testa isolamento em vez de presumir que o reset seja atômico entre threads.
