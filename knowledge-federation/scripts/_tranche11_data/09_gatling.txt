gatling-scenario-exec-sequencia||Gatling: construir workflow ordenado com exec||Um ScenarioBuilder encadeia ações com exec; requests e funções executadas no cenário seguem a sequência declarada.||Request de checkout pode rodar sem autenticação se a etapa anterior foi omitida ou a cadeia não foi ligada ao scenario correto.||Divida jornadas reutilizáveis em chains pequenas e encadeie explicitamente login, leitura, ação e verificação.||O virtual user busca carrinho, extrai id, adiciona item e conclui checkout em ações sucessivas.||Uma sequência sintática correta não garante que o estado do serviço corresponda à precondição de cada passo.||Inspecione order de requests e faça um teste pequeno que valide status e estado final antes de subir carga.||gat_scenario,gat_session||A documentação define exec como mecanismo de anexar ações sequenciais a cenários.
gatling-session-estado-por-virtual-user||Gatling: manter atributos na Session do próprio usuário||Session representa o estado de um virtual user e carrega atributos ao longo das ações do scenario.||Guardar token ou id em variável global pode misturar usuários e gerar requests cruzadas durante concorrência.||Extraia valores para Session e leia-os na expressão seguinte do mesmo usuário, sem compartilhar atributo mutável entre cenários.||Cada user extrai seu access token do login e usa esse token em request de perfil própria.||No Gatling Session é imutável; uma transformação precisa devolver a nova Session para que a alteração continue no fluxo.||Crie dois usuários com tokens distintos e confirme que cada request subsequente carrega somente seu próprio valor.||gat_session,gat_scenario||A Session API descreve estado por virtual user e ações que propagam Session; exemplos devolvem nova instância após set.
gatling-feeder-dados-variados-cache||Gatling: alimentar usuários com registros distintos para workload||Feeder fornece records aos virtual users por meio de feed e os atributos passam para Session.||Se todos os usuários consultam o mesmo objeto, caches do alvo podem ficar mais quentes que o workload real.||Prepare dataset controlado e escolha estratégia de consumo/reciclagem coerente com unicidade e tamanho necessário.||Feeder CSV dá user id e produto a cada usuário para que requests usem recursos distintos.||Dado único aumenta cobertura de objetos mas requer dataset suficiente; exhausted feeder pode falhar conforme estratégia usada.||Rode pequena população, registre records distribuídos e valide fim de arquivo, recycle e ausência de dados sensíveis.||gat_feeders,gat_session||A documentação diz que cada feed consome registro do feeder e injeta atributos na Session do usuário.
gatling-check-saveas-apos-sucesso||Gatling: validar resposta antes de guardar valor com saveAs||Checks validam request/response e podem extrair um valor para Session; saveAs só é efetivo quando check passa.||Usar valor de resposta não validada pode encadear id vazio ou incorreto em requests seguintes e produzir erro secundário.||Verifique status/estrutura e extraia somente campo que o próximo passo precisa, tratando check opcional explicitamente.||Login valida status e existência de token antes de salvar accessToken para request autenticada.||Check optional que não encontra valor não sobrescreve nem remove atributo existente; estado anterior pode permanecer.||Faça teste de resposta válida e sem campo, confira falha/optional e verifique que token antigo não é reutilizado sem intenção.||gat_checks,gat_session||A documentação cobre validação, extração e condição de saveAs efetiva somente após check bem-sucedido.
gatling-assertions-criterios-de-simulacao||Gatling: expressar pass fail com assertions de estatísticas||Assertions na Simulation definem critérios sobre estatísticas globais ou escopos como requests/grupos.||Gerar relatório sem threshold pode deixar run com alta taxa de erro ser interpretada como aprovada.||Defina limites de erro e latência que correspondam ao SLO e a população executada, com escopo nomeado.||Teste falha se percentagem global de requests bem-sucedidas cair abaixo do critério definido.||Threshold depende do workload e ambiente; usar percentil médio ou valor sem baseline não cria critério confiável.||Injete uma falha controlada e confirme que assertion muda o resultado final da execução.||gat_assertions,gat_checks||A documentação diz que Assertions verifica estatísticas da simulação e pode usar escopos globais ou detalhados.
gatling-open-closed-injection-model||Gatling: escolher open ou closed conforme hipótese de carga||Perfis open injetam usuários por taxa de chegada; closed model define concorrência de usuários cuja duração influencia novas iterações.||Modelo fechado pode reduzir novas chegadas quando servidor fica lento e subestimar sobrecarga comparado a tráfego independente do tempo de resposta.||Declare se interesse é usuários concorrentes ou taxa de chegada e use injectOpen/injectClosed coerente com hipótese.||API de ingestão testa chegada de eventos por segundo em modelo open; jornada com sessões concorrentes limitadas usa closed.||Perfis e formas de injection variam por DSL e produto; não compare execuções sem registrar modelo.||Inspecione virtual users ativos, taxa de chegada e response time durante degradação para validar dinâmica observada.||gat_injection,gat_scenario||A referência distingue injeção open e closed e documenta sequências de steps para cada modelo.
gatling-groups-agregacao-por-jornada||Gatling: nomear groups para separar estatísticas de jornada||Groups agrupam ações do usuário e permitem observar estatísticas relativas a uma parte nomeada do scenario.||Métrica global pode esconder uma chamada lenta de autenticação dentro de várias requests rápidas.||Agrupe fronteiras relevantes, use nomes estáveis e evite criar grupos por id dinâmico de usuário.||Grupo checkout contém validação de carrinho e confirmação de pagamento e tem assertions próprias de erro/tempo.||Group statistic não altera workload nem substitui métricas de sistema ou análise de dependência.||Compare métricas de grupo com global e confirme cardinalidade limitada aos nomes de jornada.||gat_scenario,gat_assertions||A documentação de scenario permite grupos e a API de assertions oferece escopo detalhado por group/request.
gatling-pauses-e-pacing||Gatling: distinguir pausa do usuário de arrival-rate injection||Pause modela intervalo entre ações do scenario; injection controla chegada/concorrência inicial de virtual users.||Aumentar pause pode reduzir requests por usuário sem necessariamente representar chegada pretendida de usuários novos.||Use pauses para think time dentro de workflow e ajuste injection profile para população e ritmo de chegada.||Usuário lê página e espera antes de enviar formulário; teste de pico separado injeta perfis crescentes.||Duração de resposta soma ao ciclo do usuário e afeta modelo fechado; pause não é garantia de RPS.||Meça request rate e users ativos após variar pause e injection separadamente.||gat_timing,gat_injection||As docs tratam timing de scenario e profiles de injeção como conceitos distintos, com pausas entre ações.
gatling-protocol-config-comum||Gatling: centralizar protocolo HTTP comum sem esconder overrides||Protocol configuration reúne base URL, headers e opções compartilhadas que podem ser associadas a um ou mais cenários.||Configuração duplicada deriva entre cenários; override global oculto pode alterar comportamento sem ficar evidente no request.||Declare configuração HTTP legível, aplique-a nos cenários pretendidos e mantenha headers específicos junto ao request que os exige.||Dois cenários usam mesmo baseUrl e accept header, enquanto fluxo admin define token em sua ação autenticada.||Defaults compartilhados não são automaticamente aplicados se protocolo não for associado ao setup do cenário.||Inspecione requests emitidos por cada cenário e faça teste de configuração quando mudar base URL ou TLS.||gat_protocol,gat_scenario||A referência de protocolo descreve configuração reaproveitável e o setup associa protocolos a cenários.
gatling-session-debug-fora-da-carga||Gatling: limitar logging e inspeção de Session fora da carga||Session pode ser inspecionada durante desenvolvimento para diagnosticar feeders, expressões e check failures.||Imprimir sessão em cada ação sob alta concorrência consome recursos do engine e pode expor token ou dados de usuário.||Ative logging em execução pequena e isolada, remova debug antes do benchmark e redija atributos sensíveis.||Um teste de smoke imprime somente chave de fixture; a simulação de carga registra métricas sem despejar Session.||Logging pode ainda afetar medição mesmo que a aplicação não mude; dados exportados exigem proteção.||Compare RPS e uso de CPU com debug habilitado/desabilitado e procure valores secretos nos artifacts.||gat_session,gat_scenario||A documentação alerta que println/debug dentro de exec é apenas para debugging e pode bloquear engine sob carga.
