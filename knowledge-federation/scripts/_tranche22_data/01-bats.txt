bats-what-it-is || bats-core: testes TAP nativos para Bash || O Bats (Bash Automated Testing System) é um framework de testes aderente ao TAP para Bash 3.2 ou superior, feito para verificar que os programas UNIX que você escreve se comportam como esperado. || Scripts de shell, wrappers de CLI e utilitários de infraestrutura raramente recebem suítes de teste; o Bats traz o teste automatizado para o mesmo idioma do código, sem depender de bindings de outra linguagem. || Cada arquivo de teste é um script Bash comum com blocos @test; o executável bats roda os arquivos .bats e emite resultados no formato TAP, que qualquer relatório CI já sabe interpretar. || bats teste.bats imprime ✓ em cada caso que passa e, na última linha, "2 tests, 0 failures" — sem terminal, a saída vira TAP puro. || Serve para testar qualquer programa UNIX, mas é onde o software escrito em Bash que ele brilha; lógicas complexas demais merecem migração para outra linguagem. || Rode bats contra um comando qualquer e confirme que a saída sem terminal começa com "ok 1 ..." no padrão testanything.org. || bt_readme,bt_index || Conferi a definição, a aderência ao TAP e o recorte "qualquer programa UNIX" no topo do README oficial.
bats-test-syntax || bats-core: a suíte é um script Bash || O arquivo .bats é avaliado como script Bash e cada caso é declarado com @test "descrição" { corpo }, que o pré-processador converte em uma função cujo nome é a descrição do teste. || Manter o teste dentro da sintaxe nativa do shell evita camadas de tradução: você usa pipes, variáveis e funções de Bash sem aprender um DSL novo. || O pré-processador reescreve cada bloco @test em função; o documento inteiro é executado n+1 vezes — a primeira passada conta os casos e depois cada teste roda em seu próprio processo. || @test "foo imprime uso" { run foo; [ "$status" -eq 1 ]; } vira uma função de teste com esse título exato no relatório. || Como o arquivo é reavaliado a cada caso, código solto fora de @test roda várias vezes; efeitos colaterais no topo do arquivo surpreendem quem espera execução única. || Escreva um echo fora de @test e conte quantas linhas ele imprime ao rodar o arquivo com dois testes declarados. || bt_docs,bt_readme || Conferi o modelo de avaliação n+1 e a expansão de @test em função na página Writing tests da documentação oficial.
bats-errexit-assertions || bats-core: cada linha viva é uma asserção || Os testes Bats rodam sob errexit: o teste termina na primeira linha com status de saída diferente de zero, de modo que toda linha que sobrevive foi verificada. || Em shell não existe exceção por igualdade, então a semântica de "falhou, aborta" transforma qualquer comando em asserção implícita e reduz a verbosidade dos casos. || Escreva os passos como comandos encadeados e termine com o teste booleano desejado, por exemplo um [ "$x" = "esperado" ]; não é preciso envolto nada em assert. || [ "$(foo)" = "bar" ] dentro do bloco @test reprova o teste se foo imprimir qualquer outra coisa, e nenhuma linha seguinte é executada. || Há pegadinhas conhecidas: negações com ! e compostos entre colchetes duplos ou aritméticos em certos contextos não chegam a falhar o teste, como a própria página de gotchas lista nos títulos. || Reproduza um teste com uma linha falsa no meio e confirme que o caso para ali; depois compare com as entradas de gotchas sobre colchetes duplos e ! true. || bt_readme,bt_gotchas || Conferi a explicação de errexit no README e a lista de pegadinhas relacionada no índice oficial da documentação.
bats-run-status-output || bats-core: run captura status e saída || O helper run invoca seus argumentos como comando, guarda o código em $status, junta stdout e stderr em $output e sempre retorna 0 para que as asserções seguintes sejam executadas. || Testar CLI exige inspecionar saída e código de erro sem abortar o teste antes da verificação; o run separa a execução bruta da checagem deliberada. || Depois do run, afirme [ "$status" -eq 1 ] e compare $output; com a versão moderna, [ "${lines[0]}" = ... ] checa linha a linha e $BATS_RUN_COMMAND devolve o comando inteiro reconstruído. || run foo nonexistent_filename seguido de [ "$output" = "foo: no such file 'nonexistent_filename'" ] documenta o contrato de erro do programa testado. || run sem as flags de expectativa engole o fracasso do comando testado; o guia traz a entrada "run doesn't fail, although the same command without run does" justamente para esse mal-entendido. || Use run -1 para exigir status 1, ou run ! para exigir status não zero, e veja o teste falhar sozinho se a expectativa não se cumprir. || bt_docs,bt_usage || Conferi as variáveis $status, $output e $BATS_RUN_COMMAND e os modos run -N / run ! na página Writing tests.
bats-setup-teardown || bats-core: ganchos por teste e por arquivo || A dupla setup e teardown funciona como pre- e pós-gancho de cada caso, e a documentação dedica uma seção do tutorial a evitar setups caros repetidos a cada teste. || Criar fixture em todo caso sai caro em suítes grandes; conhecer a granularidade dos ganchos deixa o setup por arquivo quando o estado é compartilhado e o por teste quando não é. || Declare setup no topo do arquivo para preparar TMPDIR ou instalar um binário de teste; rode o gancho inverso para limpar, confiando que o processo isolado de cada teste não vaza estado. || setup { mkdir -p "$BATS_TEST_TMPDIR/fixtures"; cp fixture.txt "$BATS_TEST_TMPDIR"; } dá a cada caso um diretório temporário virgem. || Como cada teste roda em processo próprio, variáveis exportadas em setup não sobrevivem entre casos — e o gancho também não roda em código fora de @test. || Force um teste a escrever em arquivo fora de BATS_TEST_TMPDIR e veja o segundo caso herdá-lo; depois mova para o tmpdir e confirme o isolamento. || bt_docs,bt_tutorial || Conferi os ganchos listados em Writing tests e a seção "Avoiding costly repeated setups" do tutorial oficial.
bats-tagging || bats-core: tags, filtros e modo foco || Desde a versão 1.8.0 o Bats traz tags nativas: diretivas # bats test_tags= e # bats file_tags= anexam rótulos aos casos, e --filter-tags decide o que roda combinando os rótulos. || Separar smoke tests de suítes longas por nome de arquivo é frágil; tags dão uma dimensão de seleção ortogonal ao caminho e ao regex de --filter. || A diretiva de tags vale para o próximo @test encontrado e é esquecida depois; file_tags vale para todos os testes do arquivo até outra diretiva sobrepujar; tags aceitam alfanuméricos, _, - e : como separador de namespace. || bats --filter-tags smoke,cli !slow seleciona o que tem as duas tags positivas e não tem slow; múltiplas ocorrências do flag formam um OU lógico. || Listas com tag vazia ("test_tags=,b") são rejeitadas, e qualquer tag começando com bats: é reservada ao uso interno do framework. || Rode bats -c com --filter-tags e confira que a contagem de casos muda conforme o conjunto selecionado, sem executar nada. || bt_docs,bt_usage || Conferi a sintaxe das diretivas, o jogo de caracteres permitido e a semântica booleana de --filter-tags na página Writing tests.
bats-focus-mode || bats-core: o que fica marcado roda sozinho || A tag especial bats:focus faz o Bats filtrar a suíte inteira para executar apenas os casos com ela, e em modo foco o código de saída de uma passada limpa vira 1 de propósito. || Quem desenvolve testes marca um caso com focus para iterar rápido, mas o commit acidental desse marcador deixaria o CI verificando um subconjunto silencioso — o código de saída forçado é a proteção contra isso. || Tague o teste com bats:focus, rode bats normalmente e veja só ele executar; se precisar do exit code verdadeiro (um git bisect, por exemplo), exporte BATS_NO_FAIL_FOCUS_RUN=1. || # bats test_tags=bats:focus sobre o caso "aceita --dry-run" concentra o run nesse teste durante o desenvolvimento. || O guia avisa explicitamente para não commitar a exceção BATS_NO_FAIL_FOCUS_RUN junto com a suíte, pois ela desarma a trava de segurança do modo foco. || Deixe um bats:focus esquecido num arquivo e confirme que o pipeline falha mesmo com todos os testes verdes. || bt_docs,bt_index || Conferi a seção de especial tags (bats:focus e BATS_NO_FAIL_FOCUS_RUN) documentada na página Writing tests.
bats-parallel || bats-core: --jobs com GNU parallel || Por padrão o Bats executa tudo serialmente, mas aceita paralelismo com -j/--jobs quando há GNU parallel (ou substituto compatível) instalado, acelerando suítes cujo gargalo é o custo de processo por teste. || Cada teste já roda em processo próprio por isolamento, então a estrutura suporta a concorrência sem redesign — o ganho aparece justamente em arquivos com muitos casos curtos. || bats --jobs 4 testes/ distribui os arquivos e os casos entre workers; --no-parallelize-across-files e --no-parallelize-within-files reprimem cada um dos dois eixos separadamente. || Uma suíte de 200 casos de CLI cai de vários minutos para o tempo do gargalo de E/S quando paralelizada em quatro jobs. || A ordem dos testes paralelos não é garantida; a documentação recomenda rodar várias vezes ao ativar --jobs para caçar dependências entre testes e comportamento não determinístico. || Alterne dois runs com --jobs 8 num mesmo dataset e compare as saídas; qualquer diferença de resultado denuncia estado compartilhado. || bt_usage,bt_index || Conferi os flags -j, os dois controles de granularidade e o aviso de ordem na seção Parallel Execution da página Usage.
bats-formatters || bats-core: pretty, TAP, tap13 e JUnit || O Bats escolhe o formato de saída sozinho: no terminal mostra ✓ e ✗ com resumo humano; sem terminal (CI, pipe) despeja TAP. O flag -F/--formatter força pretty, tap, tap13, junit ou um executável absoluto customizado. || Integrar um framework de shell a agregadores de relatório depende de falar a língua deles; trocar o formatter não muda um único caractere dos testes. || --report-formatter aceita as mesmas opções e grava o arquivo de relatório no diretório atual ou em --output; no histórico, o flag separou o stdout do arquivo justamente para o formato junit. || bats --report-formatter junit teste.bats --output /tmp gera /tmp/report.xml com <testsuite name="teste.bats" tests="2" failures="0" .../> e tempos por caso. || A linha "T" de timing e o -T do CLI são controles separados do formatter; quem confunde as duas coisas perde horas comparando diffs de relatório. || Compare byte a byte a saída com --formatter tap contra a saída redirecionada sem terminal e confirme que ambas começam com o plano "1..2". || bt_usage,bt_index || Conferi a lista completa de formatters, o comportamento por omissão sem terminal e o exemplo de report.xml na página Usage.
bats-fork-history || bats-core: do repositório parado ao fork comunitário || O Bats original de sstephenson parou de evoluir; em 19 de setembro de 2017 a comunidade forkou o projeto no commit 0360811 usando git clone --bare e --mirror para preservar o histórico, e o repositório antigo foi arquivado somente-leitura em 29 de abril de 2021. || Saber a linhagem importa ao ler tutoriais antigos: sintaxe e flags publicados antes de 2017 referem-se ao upstream morto, e o canonical atual é o GitHub bats-core com docs no readthedocs. || O projeto é MIT; versões anteriores à v1.2.1 têm documentação separada em docs/versions.md dentro do repositório, sinal de compatibilidade mantida entre gerações. || git log --oneline --grep=0360811 no clone do bats-core localiza o commit herdado do upstream original. || A biblioteca de exemplos oficiais mora em docs/examples no mesmo repositório, mas quem copia snippets de blogs pré-2017 pode encontrar run antigo sem --flag de status. || Diferencie uma behavior de versão checando docs/versions.md: se o recurso não está lá, provavelmente veio do upstream abandonado. || bt_readme,bt_versions || Conferi a data e o método do fork, o arquivamento do repositório original e a nota de versões antigas no README oficial.
