honggfuzz-what-it-is || Honggfuzz: fuzzer evolutivo orientado a feedback || O README oficial define o Honggfuzz como "a security-oriented, feedback-driven, evolutionary fuzzer", um fuzzer de propósito geral que usa cobertura de código — de software e de hardware — para encontrar bugs, com engine multi-processo, multi-thread e suporte a persistent fuzzing "for extreme speed". || A combinação das três palavras do lema importa: security-oriented significa que o alvo declarado são vulnerabilidades exploráveis; feedback-driven que a evolução dos inputs é guiada por sinais de execução; e evolutionary que o corpus cresce por mutação e seleção, não por geração cega. || O motor executa o binário instrumentado com inputs mutados, mede cobertura (inclusive via hardware), mantém e expande o conjunto de inputs interessantes e distribui o trabalho entre processos e threads para ocupar todas as CPUs. || Comece pelo binário alvo instrumentado e "honggfuzz -i corpus/ -- ./alvo ___FILE___": sem nenhum input inicial, a ferramenta evolui o corpus do zero. || O README é sucinto por design; o detalhamento de opções vive em docs/USAGE.md, referenciado como a doc de uso avançado que esta nota apenas endereça. || A definição, os três adjetivos e o modelo multi-processo/thread estão no topo do README oficial. || hfg_readme,hfg_repo || O parágrafo introdutório do README oficial sustenta a definição.
honggfuzz-hardware-coverage || Cobertura de hardware: Intel BTS/PT como motor de feedback || Entre os key features, o README lista "Feedback-Driven: Uses hardware (Intel BTS/PT) and software code coverage to evolve inputs" — o fuzzer aproveita os recursos de rastreamento de branch do hardware Intel (BTS/PT) além da instrumentação por software. || Cobertura medida em hardware não depende de recompilar o alvo com instrumentação: abre caminho para fuzzar binários complexos com menos atrito de build e com menos distorção de performance, o que muda a taxa de execução efetiva em alvos grandes. || Use a instrumentação por software (SanitizerCoverage via os wrappers) quando precisar de precisão de mapa; considere o caminho de hardware quando o alvo é caro de recompilar ou quando a sobrecarga do tracing por software compromete a vazão. || Um binário compilado com o wrapper do próprio projeto já recebe cobertura de software; o modo hardware do README (BTS/PT) é o diferencial listado como capacidade nativa do motor. || Os detalhes de quando cada fonte de cobertura é habilitada e os requisitos exatos de CPU não constam do README; a página USAGE.md linkada é o ponto de verificação. || A linha de feedback do bloco "Key Features" do README oficial nomeia BTS/PT explicitamente. || hfg_readme,hfg_docs || O uso de Intel BTS/PT é afirmado literalmente no README.
honggfuzz-persistent-mode || Persistent fuzzing com 1M de iterações por segundo || O README destaca "Persistent Fuzzing: Test APIs directly in-process with iteration speeds up to 1M/sec" — em vez de reiniciar o processo do alvo a cada input, o Honggfuzz exercita a API diretamente dentro do processo, e o modo é acionado com -P no comando do README. || O gargalo clássico de fuzzing de processo único é o fork/exec por input; o modo in-process remove esse custo, e o número do próprio README (até 1 milhão/seg) dimensiona a diferença que isso faz em alvos de parsing pequeno. || Compile o alvo com o wrapper (hfuzz-clang), exponha um ponto de entrada que leia o input em processo e rode "honggfuzz -P -i input_dir/ -- ./my_target"; sem -P, o modo clássico trata o input via placeholder de arquivo. || O par de comandos do README mostra o contraste: modo básico com "___FILE___" substituído pelo caminho do arquivo, e modo persistente sem o placeholder porque o alvo lê pela API interna. || "up to 1M/sec" é o teto anunciado, não uma garantia: depende do alvo, da instrumentação e da máquina; alvos com setup por iteração caem muito abaixo disso. || A seção Usage do README lista os dois modos lado a lado, e o feature bloco quantifica a velocidade do persistente. || hfg_readme,hfg_docs || O modo -P e a taxa anunciada vêm do README oficial.
honggfuzz-empty-corpus || Começar do zero: corpus vazio que se auto-constrói || O README promete "Easy: Can start with an empty corpus and automatically build a valid input set" — a ferramenta é capaz de partir de um diretório de inputs vazio e construir sozinha um conjunto de entradas válidas. || Para formatos com estrutura forte, a maioria dos fuzzers exige seeds que passem do primeiro parser; a promessa de corpus inicial zero reduz o atrito de começar a fuzzar um formato novo, transferindo para o motor o trabalho de descobrir entradas que exercitam código. || Crie o diretório, deixe-o vazio e aponte "-i input_dir/" no comando; a evolução guiada por cobertura constrói o corpus — e o mesmo diretório continua recebendo os inputs interessantes descobertos. || O exemplo canônico do README roda exatamente assim: ./honggfuzz -i input_dir/ -- ./my_target ___FILE___ com input_dir/ vazio. || Para alvos complexos, seeds reais de corpus público aceleram muito; a nota registra a capacidade declarada de partir do zero, não a recomendação de fazê-lo sempre. || A frase do empty corpus está na lista "Key Features" do README oficial, e o exemplo de uso confirma o diretório vazio. || hfg_readme,hfg_docs || O README declara explicitamente o start com corpus vazio.
honggfuzz-ptrace-monitoring || ptrace: detectar sinais sequestrados e crashes escondidos || O README lista "Deep Monitoring: Uses low-level APIs (ptrace) to detect hijacked signals and hidden crashes" — a observação do processo fuzzado é feita em nível de ptrace, capturando situações em que o handler de sinal do próprio alvo engole a falha que o fuzzador deveria ver. || A classe de bug mais traiçoeira em fuzzing é a que não derruba o processo: crash transformado em return silencioso por um handler catch-all. Monitorar via ptrace tira essa decisão das mãos do alvo — o detector fica fora do alcance do código testado. || Rode o alvo sem mudanças no tratamento de sinais e deixe o monitor do Honggfuzz observar o processo; a detecção de crash independe de o alvo instalar handlers, porque o sinal é visto pela API de baixo nível antes do tratamento interno. || Um parser que chama exit(0) dentro do handler de SIGSEGV ainda aparece como crash para o processo de monitoramento descrito no README. || Os mecanismos internos de classificação (quais sinais contam, timeouts) não são detalhados no README; USAGE.md linkado é onde o comportamento fino é especificado. || A linha de "Deep Monitoring" do bloco Key Features do README oficial descreve exatamente esse mecanismo. || hfg_readme,hfg_docs || O monitoramento por ptrace e os alvos dele estão no README.
honggfuzz-platform-support || Seis famílias de SO: do Linux ao Windows via Cygwin || A seção de features declara "Broad Support: Linux, macOS, Android, NetBSD, FreeBSD, and Windows (Cygwin)" — o fuzzer roda no kernel Linux e nos BSDs, cobre Android e exige a camada Cygwin para Windows. || Suporte multiplataforma permite fuzzar o mesmo alvo onde a bug-hunt rende: bibliotecas portáveis nos três sistemas para pegar bugs de compilação específica, e Android como casa de componentes em produção real. || Instale dependências por SO (no Ubuntu/Debian: binutils-dev, libunwind-dev, libblocksruntime-dev e clang), rode "make" — que gera os wrappers em hfuzz_cc/ — e use o mesmo binário em cada plataforma-alvo. || O bloco de Instalação do README lista o apt-get completo para Debian/Ubuntu e o requisito de Xcode 10.8+ com libblocksruntime para macOS: build idiomático por plataforma, sem script único. || Windows é coberto "Cygwin" apenas, como o parêntese do README deixa claro; comportamento nativo MSVC não é o que a feature listada afirma. || A lista de plataformas e as dependências por SO constam das seções Key Features e Installation do README oficial. || hfg_readme,hfg_docs || O README oficial enumera SOs e dependências de build.
honggfuzz-build-wrappers || O build: make, hfuzz_cc e os wrappers de compilação || A compilação oficial é um "make" na raiz, que cria "compilation wrappers" em hfuzz_cc/; o passo 1 do uso é compilar o alvo com esses wrappers — hfuzz-clang para C e hfuzz-clang++ para C++ — para "automatically add instrumentation" ao binário. || O modelo wrapper é o mesmo do AFL/libFuzzer que a comunidade conhece: você não muda o build system do alvo, troca o compilador; isso torna a instrumentação uma decisão reversível, controlável por variável de ambiente do CI sem tocar no Makefile da vítima. || Rode make no checkout (após instalar as dependências do SO), e então "make CC=./hfuzz_cc/hfuzz-clang CXX=./hfuzz_cc/hfuzz-clang++" no projeto alvo para obter o binário instrumentado — a linha de compilação do README mostra o uso direto com -o alvo. || ./hfuzz_cc/hfuzz-clang -o my_target my_target.c é o exemplo literal do README para C; para C++, o par com hfuzz-clang++. || O README documenta o wrapper como caminho padrão; targets em outros sistemas de build (CMake, Meson) seguem o mesmo princípio de trocar CC/CXX, que a nota menciona como prática sem afirmar que o README a descreva. || Os comandos de build e de compilação do alvo são as listas literais das seções Build e Usage do README oficial. || hfg_readme,hfg_docs || Instruções de build e wrappers vêm literalmente do README.
honggfuzz-input-placeholder || ___FILE___: o contrato do input por arquivo || No modo clássico, o README define o calling convention com um placeholder explícito: "honggfuzz -i input_dir/ -- ./my_target ___FILE___", anotando que "___FILE___ is a placeholder for the input filename generated by honggfuzz". || O contrato do nome do arquivo é o ponto em que o alvo se conecta ao motor: o programa fuzzado recebe um caminho, lê o conteúdo e processa — quem entende isso escreve alvos corretos de primeira, sem pipelines ad-hoc de stdin que quebram com corpora em disco. || Escreva o main do alvo aceitando um argumento de arquivo (o caso mais simples é abrir argv[1] e parsear), ou substitua o placeholder pela fonte esperada; em qualquer variante, o diretório -i guarda o corpus de entrada e saída da evolução. || Um programa de leitura binária com fopen(argv[1], "rb") encaixa exatamente no exemplo do README; o -i do input_dir pode começar vazio conforme a outra feature listada. || A nota cobre o contrato de arquivo; o modo persistente (-P) descrito na mesma seção não usa o placeholder porque lê pela API in-process — não confunda os dois contratos de entrada. || A linha do comando e a nota do placeholder são texto literal da seção Run Fuzzer do README oficial. || hfg_readme,hfg_docs || O placeholder e seu significado estão anotados no próprio README.
honggfuzz-trophies || Trophies: a lista de CVEs como currículo || A seção Trophies do README documenta o histórico real: no OpenSSL, CVE-2016-6309 marcada "(Critical, Potential RCE)" mais três CVEs; em Apache HTTPD, CVE-2017-7659 (remote crash do mod_http2) e CVE-2017-9789 (use-after-free) entre outras; Samba com três CVEs; ProFTPD CVE-2019-18217 (DoS); FreeType 2 com a série CVE-2010-2497 até CVE-2010-2527; VLC double-free RCE; Adobe Flash CVE-2015-0316; ImageIO do iOS/macOS "Multiple security problems (Project Zero)"; e até panics do Rust em regex, h2, sleep-parser e lewton. || Para justificar investimento em fuzzing, um currículo de CVEs em software amplamente auditado (OpenSSL, OpenSSH pre-auth crash, BIND) responde à pergunta "isto acha bugs que testes de unidade não acham?" com exemplos nomeados, não com retórica. || Use a lista como mapa de onde fuzzing rende: parsing de rede (HTTPD, SSH), formatos de mídia (TIFF, JPEG, FreeType) e parsers de linguagem — e procure os IDs citados no tracker público de cada projeto antes de concluir por analogia com o seu alvo. || A entrada "Rust: Panics/safety issues in regex, h2, sleep-parser, lewton" mostra que o fuzzing vale também em memória-safe: panic é crash detectável, mesmo sem corrupção. || A lista é a autodeclaração do projeto, organizadas por categoria com IDs específicos; verifique cada CVE no documento oficial de segurança do software afetado antes de repetir qualquer afirmação além da linha citada. || Os itens foram lidos diretamente da seção Trophies do README oficial, incluindo os marcadores de severidade. || hfg_readme,hfg_repo || Os CVEs citados são os listados na seção Trophies do README.
honggfuzz-adopters-not-google || Quem adota — e o disclaimer de que não é produto Google || O README encerra com a seção "Projects Using Honggfuzz": Google OSS-Fuzz (fuzzing contínuo de open source), a equipe de segurança do Android, o crate honggfuzz-rs para Rust, Bitcoin Core, Apache HTTP Server e Systemd em CI, Cifasis QuickFuzz e Mozilla FuzzOS — e finaliza, em negrito, "__This is NOT an official Google product__", sob Apache License 2.0. || A lista de adotantes é a validação de produção: OSS-Fuzz rodando o motor contra o ecossistema open source inteiro, e o disclaimer importante para o jurídico entender a natureza do projeto (código Google, governança de projeto aberto, sem contrato de suporte). || Ao escolher um fuzz-engine, compare adotantes em produção com o seu perfil (CI de servidor? kernel? criptografia?) — o próprio README remete aos "hundreds more" nos bugs do OSS-Fuzz com filtro por honggfuzz. || O parágrafo de Rust cita o "honggfuzz-rs crate for fuzzing Rust code" como caminho da comunidade Rust, separado do wrapper C — um motor, dois pontos de entrada. || O status "not official Google product" vem do próprio README; nada aqui descreve SLA, suporte ou política de release que o projeto não afirme por escrito. || As duas últimas seções do README oficial — Projects Using Honggfuzz e License — sustentam a nota literalmente. || hfg_readme,hfg_repo || Adotantes, licença e disclaimer constam do fechamento do README.
